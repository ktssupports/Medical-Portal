# Free-tier setup: Render + Supabase

This deploys the same application and all four portals. Use the providers' Free plans where available; this repository does not create paid resources. Check [Render free service terms](https://render.com/docs/free) and [Supabase pricing](https://supabase.com/pricing) when signing up. Exact quotas are deliberately not hard-coded because providers change them.

## 1. Create the Supabase Free project

1. Create an account at https://supabase.com and create a project on the Free plan. Choose a strong database password and keep it in a password manager.
2. In the SQL editor, run `deploy/supabase-storage.sql`. Check Storage → `medical-reports` is **private**. Do not add anonymous/public file policies.
3. Under **Connect**, copy the **Session pooler** PostgreSQL URI (typically port 5432). The session pooler supports IPv4 hosting. Replace the password placeholder with your URL-encoded database password and append `?sslmode=require` (or `&sslmode=require` if the URI already has options).
4. Copy the project URL (`https://PROJECT_REF.supabase.co`) and the server-only legacy **service_role** API key from project API settings. Keep it secret. Do not use the anon/publishable key here. The storage REST adapter sends the legacy service-role JWT as a bearer token.

## 2. Deploy the free Render application

1. Create/connect an account at https://render.com. Choose **New → Blueprint**, connect your GitHub account, and select `ktssupports/Medical-Portal`. Select branch `main`.
2. Render reads `render.yaml`, which requests one **free** Python web service and no paid database/disk. Review the resource plan before confirming. If Free is not offered for your account/region, stop rather than choosing a paid plan.
3. Supply the requested secrets in Render:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Supabase Session pooler URI with TLS |
| `SUPABASE_URL` | Project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only legacy service-role JWT |
| `INITIAL_ADMIN_PASSWORD` | A new unique password, minimum 12 characters |

`SECRET_KEY` is generated by the Blueprint. Initial admin ID defaults to `ADM-101`. Do **not** add `DEMO_MODE=1` in production.

4. Deploy. Startup runs `python manage.py` to initialize the schema and create the first administrator only when there are no existing accounts, then starts Gunicorn. The server stores no production records on Render's ephemeral disk.
5. Once deployment succeeds, open the **actual onrender.com URL shown in your Render dashboard**, sign in as `ADM-101` with your chosen password, and remove `INITIAL_ADMIN_PASSWORD` from Render environment settings. Existing database users prevent bootstrap from running again.
6. Run `deploy/supabase-hardening.sql` in Supabase's SQL editor. Confirm `medicore` is not listed in Data API exposed schemas. This prevents direct browser access to application tables.
7. Create provider accounts under Accounts & approvals; approve them to enable login. Register patients and create their corresponding patient accounts. Assign doctors or let patients manage permissions. Doctors can create orders for approved lab accounts.

## 3. Backups on a free allowance

Supabase Free should not be assumed to include managed automatic backups or point-in-time recovery. The included GitHub Actions workflow runs daily at **08:00 Asia/Kolkata** (02:30 UTC), and can also be run manually. Scheduled Actions require the workflow on the default branch and may be disabled after repository inactivity or delayed by GitHub.

Set these **GitHub repository Actions secrets** (never repository variables or files):

- `BACKUP_DATABASE_URL`: Supabase Session pooler URI with TLS, authorized to read `medicore`.
- `BACKUP_ENCRYPTION_KEY`: a Fernet key generated locally: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` after installing `cryptography==46.0.3`. Save a second copy in your password manager; losing it makes backups unrecoverable.

The workflow uses PostgreSQL 17 tools. Match the image major version to your actual PostgreSQL server version if it differs. It dumps the `medicore` schema only, encrypts the dump before writing an artifact, and retains encrypted artifacts for seven days. GitHub usage/storage allowances apply; monitor usage. Anyone with artifact access can download ciphertext; the encryption key must remain private. **Report blobs are not backed up by this database workflow.** Export the private bucket separately to another encrypted storage destination if you require report recovery. A complete data backup strategy is not fulfilled until both database and files are covered.

Restore into an empty **separate test database** with matching PostgreSQL tools:

```sh
# DATABASE_URL_RESTORE and BACKUP_ENCRYPTION_KEY are loaded from your secret manager.
# Do not print or commit their values.
set -o pipefail
python deploy/restore.py medical-portal.dump.enc | pg_restore --no-owner --no-acl --dbname="$DATABASE_URL_RESTORE"
```

Test login, sample readings, permissions and report metadata after restore. Configure retention and rehearse recovery before storing real data. Never test a restore against the live database.

## 4. Monitoring and limits

- Render checks `/health`; the endpoint returns 503 if PostgreSQL is unavailable. Review Render and Supabase logs. Set up free external health alerts with a monitoring provider you choose; none is connected automatically.
- Free Render services may spin down when idle and take time to wake; Supabase Free projects may pause. Database space, file storage, egress, build minutes and backup artifact storage are limited.
- A basic free demo is possible. Production availability and medical compliance are not guaranteed by these free plans. Use synthetic data until the hosting/storage agreements and operations match your requirements.

## Troubleshooting

- Login loops: keep HTTPS on Render and a stable SECRET_KEY; do not enable demo mode.
- Database connection errors: use Session pooler hostname/user, URL-encode password, require TLS, verify project is running. Use the documented Session pooler; the application sets its own schema search path on each connection.
- Permission errors after hardening: use the Supabase database owner connection as described, or provision a dedicated server role with access/BYPASSRLS; do not expose the schema to browser roles.
- Upload fails: verify private bucket name and service-role JWT. The API deliberately returns a generic storage error instead of logging credentials/provider responses.
- Empty deployment: the repository alone does not create provider accounts or secrets. A live URL exists only after Render completes deployment.

## Reset an existing administrator password

If `ADM-101` is approved but rejects the password, add `RESET_ADMIN_PASSWORD` in the Render service's Environment settings with a new unique password of at least 12 characters. Save and deploy the latest `main` commit. The initializer resets only the approved administrator named by `INITIAL_ADMIN_ID` (default `ADM-101`), revokes its old sessions, clears its login attempt limit, and records an audit event. No password is printed. Repeated starts with the same value do not reset it again or revoke fresh sessions.

Sign in with the new password, then **remove `RESET_ADMIN_PASSWORD`** and save/deploy. The password remains saved as a salted hash in PostgreSQL. Changing `INITIAL_ADMIN_PASSWORD` alone only affects first-account creation and does not reset an existing account.
